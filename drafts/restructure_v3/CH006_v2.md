# CH006《未完成》— v2

> 状态：V3 CANDIDATE
>
> 硬推进：
> 未完成公共责任原则 → 跨版本保留是正常设计 → 2035状态曾减弱 → 2036无明确人工修改却重新增强 → 追溯到2032紧急回滚补丁。
>
> 阶段钩子：异常的制度根源指向2032，进入“黑箱”阶段。

梁慎之拿来的旧规范有二十七页。

标题：

**跨版本未完成事项保留规范。**

沈既明看到这个名字时，以为终于会出现一份“答案”。

翻开以后，全是制度。

平台升级时什么要迁。

组织调整时什么不能丢。

历史责任怎样交接。

第九页有一句加粗：

**系统版本升级、平台迁移或组织调整，不得自动清除尚未完成的公共责任状态。**

梁慎之说，这条原则本身一点都不神秘。

城市系统以前换过平台。

事故工单可以结案，但三个月后的复查还没做；某项治理项目可以完成施工，但承诺的一年跟踪还没结束。如果只迁“当前工单”，旧系统一关，后续责任就跟着消失。

所以早期设计者做了一件很朴素的事。

软件可以换。

没做完的责任不能因为软件换了就没了。

沈既明听到这里，第一次觉得柳桥新村那个长期状态也许并不异常。

程见微也得出同样结论。

如果只是“跨版本保留”，那是设计目标，不是智能行为。

真正需要查的是2036。

因为他们把迁移前后的历史状态重新对齐以后，宋亦衡找到一个断点。

2035年底，柳桥新村的“历史未完成风险”已经被降成弱关联。

这是合理的。

维修做过，几年没有严重积水，旧风险应该逐渐变轻。

但到了2036暴雨前，这个状态重新增强。

不是恢复原字段。

不是简单从旧数据库复制回来。

它在新的版本里以新的结构重新获得了更高权重。

沈既明第一反应是有人改过。

他们查了人工记录。

没有。

又查是否有新的居民投诉直接把它拉高。

没有完全对应的触发。

程见微仍然不允许把它写成“系统自己重新判断”。

她只接受一句：

**当前未找到足以解释该权重重新增强的明确人工操作或单一规则触发。**

沈既明嫌这句话长。

这一次却没嫌它慢。

因为他知道差别有多大。

如果状态一直没断，是工程设计。

如果状态变弱以后，因为新环境、新数据和历史后果再次被拉高，而没有一个明确的人重新把它挂回去——

他们正在接近另一种东西。

宋亦衡没有被“聪明”吸引。

他盯着2036那次资源排序，只问：

“它把柳桥新村提上去了，哪一个地方就被往后放了？”

没人能马上回答。

资源不是无限的。

一次正确的偏移仍然意味着另一边承担了机会成本。

梁慎之听到这里，第一次收起那种“让学生自己查”的态度。

他让所有人暂停继续扩大样本，只查这条长期状态本身。

这不是因为他认为系统已经有主体性。

而是因为他认出了那份规范的来路。

跨版本保留原则并不是协六时代才有。

继续追修订历史以后，他们看到的不是一个干净的设计版本，而是一段被反复改过的历史。

2031年，企业侧已经出现“长期行为漂移”观察。

2032年，栖州城市平台发生过一次紧急回滚。

现有资料里，有一条复核备注把两件事直接连在一起：

**长期行为漂移相关记录，建议与2032回滚异常合并复查。**

没有解释为什么。

更关键的是，2032回滚前后的历史材料不完整。

版本变更记录还在。

责任状态迁移记录还在。

回滚动作本身也能确认。

但用于解释“为什么必须回滚”的那部分事故材料，没有出现在当前共享档案里。

梁慎之看到这里，第一次主动让他们停下来。

不是“今天先到这”。

而是明确地说：“后面的材料先别碰。我去确认权限。”

沈既明抬头。

这和以前不一样。

以前梁慎之限制他们，是因为证据不够。

这一次，是因为他知道前面是什么。

程见微没有追问。宋亦衡也没有。

陆峥只问2032这部分属于什么权限。

梁慎之沉默了一会儿。

“不是级别的问题。”

说完，他把那几份材料收了起来。

最上面那页仍露着一行字：

**2032 回滚异常。**

北连廊以前，他们查的是一条提前十五分钟出现的消息。

六章以后，那条消息已经把他们带到一段连梁慎之都不愿意让学生直接碰的历史。

而那段历史，早在他们目前知道的所有异常之前。
